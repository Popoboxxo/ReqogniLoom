### 2.1 Ziel & Scope / Nicht-Ziele

**Ziel.** Die Hermes-Integration von einem POC-Dashboard (drei Zahlen, eigener `urllib`-REST-Client)
zu einer **agenten-nativen** Anbindung umbauen: Der Hermes-Agent bedient ReqogniLoom über den
vorhandenen **MCP-Stack** (223 Tools laut `docs/agent-templates/tool-manifest.json`), der
Interview-Fluss läuft **im Agenten-Dialog** über `interview.chat`/`interview.set_target`, der
Ambient-Capture aus #1156 speist denselben Pfad, und der Dashboard-Tab bleibt ohne
Token-Handling und mit Workspace-Picker.

**Ausgangslage (belegt):** `integrations/hermes-agent-plugin/` (Python) nutzt einen eigenen
stdlib-REST-Client (`reqogniloom_client.py`), der die `/api/v1/`-Fläche direkt spricht; das
README hält selbst fest, dass `interview.chat` „on the REST surface but not among the MCP tools"
sei (Zeilen 378–381) — **dieser Stand ist durch #1164 überholt**: `interview.chat` existiert als
MCP-Tool (`docs/agent-templates/tool-manifest.json:3433`), ebenso `interview.set_target` (`:3593`)
und die `memory.*`-Gruppe (`:4168`ff.). Das alte TS-Plugin
`integrations/hermes-plugin/reqogniloom/` ist laut README (Zeilen 37–43) „very likely dead code".

**Nicht-Ziele.** Kein neuer REST-Client; kein paralleler zweiter Integrationspfad; keine
Neuentwicklung der MCP-Fläche (die Tools existieren).

### 2.2 Vorbedingungen / Entscheidungen

- **#1203 (F1/F2/F4) ist gelöst**; **#1202 F5/F6/F7** erledigt (PR #1207). Offen ist **#1202-F3**
  (siehe §3) — #1201 setzt auf dem F3-Umbau auf.
- **MCP-Fläche vorhanden:** `interview.chat` (#1164), `interview.set_target`, `memory.*`,
  `traceability.*` — kein Manifest-Neubau nötig.
- **Entscheidung E-Hermes-1:** Welches Artefakt ist das produktive Hermes-Integrationspaket?
  Empfehlung: das **Python-Agent-Plugin** (`integrations/hermes-agent-plugin/`) konsolidieren,
  das TS-POC (`integrations/hermes-plugin/`) als tot markieren/entfernen (Folge-ADR-017-Kontext:
  Plugin-Versionierung ist Nicht-Produkt-Zusage, `plugin.yaml` `0.1.0` + `minServerVersion`).
- **Entscheidung E-Hermes-2:** Dashboard-Tab „ohne Token-Handling" — die opt-in

  der Tab nutzt den **server-seitig konfigurierten** API-Key (kein Operator-Token im Browser).
  Das setzt voraus, dass der Host den Tab authentifiziert (Host-Auth als Gate).

### 2.3 Zielarchitektur (code-verankert)

- **MCP statt REST.** Der Agent (und der Capture-Worker) sprechen `interview.*`, `memory.*`,

- **Interview im Agenten-Dialog.** `interview.start` → `interview.get_state` →

  `interview.chat` ist MCP-Tool (`tool-manifest.json:3433`); `reply`-Feld bleibt die reale
  Antwortform (`backend/application/interview_service.py:1986`).
- **Ambient-Capture (#1156).** Der `pre_llm_call`-Hook (README §Listen mode) reicht eine
  Nachricht an einen detached Worker (`_capture.py`); statt REST-`/chat/` wird künftig
  `interview.chat` über MCP genutzt; der Vorschlag wird in die **Review-/Accept-Fläche** überführt.
  Die Vorschlags-Hälfte hängt am generischen Accept-Pfad (ADR-019, §1).
- **Dashboard-Tab.** `dashboard/plugin_api.py` (FastAPI-Router) + `dashboard/dist/index.js`:

## 4. #1204 — Qdrant als optionales Vektor-Backend stattdessen

| Feld | Wert |
|---|---|
| **Status** | Entwurf — Planung (RFC → ADR nötig) |
| **Datum** | 2026-10-07 |
| **Bezug-Issues** | #1204 (Leit) · #1132 (celery-beat lädt Embedding-Modell ~407 MiB) · #1178 (Duplikaterkennung) · #794/#826/#977 (Embedding-Dimension/HNSW/iterative Scan) |
| **Geltung / Scope** | Optionaler externer Vektordienst Qdrant für die Memory-Domäne (V1) und perspektivisch die Artefakt-Suche (V2) über eine neue Vektor-Port-Abstraktion; Compose-`profiles`-Muster |
| **Nicht-Teil** | Ersatz der pgvector-Pflicht; Zwang zu externem Dienst; V2 im ersten Schnitt |

### 4.1 Ziel & Scope / Nicht-Ziele

**Ziel.** Qdrant als **optionalen** zusätzlichen Vektor-Backend anbieten — ohne pgvector als
Default zu ersetzen. Der RFC-Stand ist **code-verifiziert** (siehe §4.2). Da der RFC eine
**bestehende Architektur-Entscheidung revidiert** (Doku lehnt externen Vektordienst ausdrücklich
ab), ist **zuerst ein ADR Pflicht** (`proposed`), bevor irgendein Code entsteht.

**Nicht-Ziele.** Kein Entfernen der pgvector-Implementierung; kein neuer Vektordienst als
Pflicht-Service im Default-Compose; V2 (Artefakt-Suche) ausdrücklich erst nach V1.

### 4.2 Code-verifizierter Ist-Stand

- **Vier Vektor-Spalten** (`backend/persistence/embedding_dimensions.py:11-14`):
  `pl_requirement.embedding` (`backend/persistence/models.py:1602`),
  `pl_tracelink.embedding` (`backend/persistence/models.py:1946`),
  `icd_icd.embedding` (`backend/icd/models.py:148`),
  `mem_memory_entry.embedding` (`backend/memory/models.py:97`).
- **Nur der Memory-Zugriff ist abstrahiert:** `MemoryBackend.query` /
  `backend/memory/backends.py` (Registry `:523`/`:526`, `get_memory_backend` `:536`,
  `PgvectorMemoryBackend` `:662`, `query` `:863`) + `backend/memory/honcho_backend.py`
  (`register` `:513`, `query` `:1453`).
- **Vier direkte ORM-ANN-Sites** (kein Port, direkte `CosineDistance`-Nutzung):
  - `backend/application/search_service.py:608` (Requirement),
  - `:631` (TraceLink),
  - `:661` (Icd),
  - `backend/application/requirement_service.py:1001`,
    `backend/application/trace_link_service.py:915`, `backend/icd/icd_manager.py:720`.
- **Einbaustelle Backend-Registry:** `backend/memory/backends.py` + Pflicht-Import in
  `backend/memory/apps.py:67` (Muster: `import memory.honcho_backend`) — ohne Import fehlt der
  Name in `MEMORY_BACKEND_REGISTRY` („unknown memory backend").
- **Optional-Service-Muster:** Compose-`profiles` wie `honcho`
  (`deploy/docker-compose.yml:1137`ff.) und `bluepencil` (`:1453`).
- **Konflikt:** `docs/se/L1/Gesamtsystem/L2/VectorSearchServiceSystem/L2_VectorSearchServiceSystem_Requirements.md:32,36`
  legt „embedded pgvector, kein externer Vektordienst" fest → ADR-Zwang.

### 4.3 Vorbedingungen / Entscheidungen

- **ADR-020 (neu, `proposed`):** „Qdrant optional als Vektor-Backend" — mit
  **Entscheidung A/B (Collection-Strategie):**
  - **A — eine Collection pro Tenant/Workspace** (Isolation über Collection-Namen/Filter),
  - **B — eine Collection mit Payload-Filter** (`tenant_id`/`workspace_id` im Payload).
  Die Wahl berührt Tenant-Isolation (RLS-Analogon) — Threat-Model nötig.
- **V1/V2-Schnitt:**
  - **V1 = nur Memory** (nutzt die vorhandene `MemoryBackend`-Abstraktion → minimaler Fußabdruck).
  - **V2 = Artefakt-Suche** über einen neuen **Vektor-Port** über den vier ORM-ANN-Sites —
    Folgeentscheidung/-ADR.
- **Default bleibt pgvector**; Qdrant nur per `MEMORY_BACKEND=qdrant` + Profil.

### 4.4 Zielarchitektur (kurz)

- **V1:** Neuer `QdrantMemoryBackend` (`backend/memory/qdrant_backend.py`) registriert via
  `@register_memory_backend("qdrant")`; Import in `backend/memory/apps.py`; nutzt die vorhandene
  `MemoryBackend`-Oberfläche. Offene Frage: Verhältnis zur kanonischen `MemoryEntry`-Zeile
  (Metadaten bleiben in Postgres, Vektoren in Qdrant — Mapping-Tabelle/`backend_ref`).
- **Optional-Topologie:** Compose-Service `qdrant` mit `profiles: ["qdrant"]` + Volume;
  Healthcheck; kein Host-Port nach außen (Muster honcho intern).
- **V2 (Folge):** Vektor-Port-Interface in `application/` (oder Layer 0), Adapter pgvector/Qdrant;
  die vier `CosineDistance`-Sites werden auf den Port umgestellt. `#1178` (Duplikaterkennung)
  kann den Port mitnutzen.
