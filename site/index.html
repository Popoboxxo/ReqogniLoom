What it is

One model for requirements, architecture, tests and decisions

Requirements engineering, architecture modelling and test management usually live in separate tools, so traceability is reconstructed by hand and AI assistants cannot reach the data. ReqogniLoom keeps all of it in one artifact-based model with trace links as a first-class citizen.

The problem

Siloed tools, manual traceability matrices and decisions that are not linked back to the requirements they affect. Documentation drifts away from the system it describes.

The approach

One codebase with a single domain façade. REST and MCP are thin transport adapters over the same application services, so a UI action and an AI tool call follow the identical rules.

Three rigor levels

The same data model adapts from a lightweight backlog (minimal) to a formal systems-engineering workflow (extended) — no fork, no separate product.

Capabilities

Core capabilities

Open a capability to see what it actually does. Each entry expands in place and stays keyboard-operable.

Create and organize requirements with workflow states and categories, and model MBSE-compatible architecture elements across decomposition levels. Ideas flow through Stakeholder Needs and requirements into architecture, test cases, ADRs, risks, issues and glossary terms.

Automatic and manual linking between requirements, architecture elements and test cases with 11 core link types (tenant-extensible catalog), coverage aggregation and an interactive impact analysis across both directions.

Attach test cases to requirements, track coverage, and record test runs with bulk result ingestion over both REST and MCP. A four-phase lifecycle keeps results auditable instead of overwriting history.

Capture snapshots at document, project or global scope and compare system states over time, including field-level artifact diffs with side-by-side and unified highlighting for requirements, architecture elements and test cases.

Configurable state machines per workspace with validated transitions, approval gates and review policies that can gate AI-derived artifacts before they are accepted.

Atomic CSV bulk import for requirements, architecture elements and test cases, PDF export for requirement documents and traceability matrices, a per-artifact history endpoint, and API-key management for CI/CD integrations.

Full-text search plus a semantic (RRF-fused) pass, an optional cross-workspace scope, and a two-tier AI long-term memory (per-workspace and per-user) stored in PostgreSQL with pgvector.

Row-level tenant isolation, an RBAC matrix with item-level permissions, operation-level audit logging, terminology profiles for dev and systems-engineering audiences, and German / English interfaces.

Traceability

V-Model traceability from stakeholder needs to presentation

Every artifact carries a REQ identifier and can be linked upward and downward, so a change at one level can be traced to everything it affects.

  1. L0

    Stakeholder Needs

    What the stakeholders actually need, captured before a solution is chosen.

  2. L1

    System Requirements

    Verifiable system-level requirements derived from stakeholder needs.

  3. L2

    Subsystems

    Architectural decomposition into subsystems that carry allocated requirements.

  4. L3

    Components

    Concrete components and interfaces with their own requirements and tests.

  5. L4

    Presentation

    The presentation and behaviour layer where the system meets its users.

What flows between the levels

Derivation runs downward (needs to requirements to architecture), verification runs back up: test cases are linked to the requirements they verify, so coverage gaps are visible instead of assumed. Links are added explicitly or derived with AI support, and the full chain stays queryable.

Trace links as data, not documents

Links are stored entities, not rows in a spreadsheet. They can be typed, queried, exported as a traceability matrix PDF, and audited through the same history endpoint as every other artifact.

AI & MCP

Built for AI assistants, not bolted on

ReqogniLoom speaks Model Context Protocol natively, so an assistant works with the same requirements and tests a person sees — no export, no snapshot, no separate integration layer.

Native MCP server

JSON-RPC 2.0 over HTTP, SSE and stdio. Authentication uses API keys (prefix reqlo_) or a bearer token. The same server serves Claude Desktop, Cursor, OpenCode and Codex CLI.

  • 31tool-group prefixes
  • 188individual tools
  • 3transports

Pluggable LLM adapters

Anthropic, OpenAI, Azure OpenAI, Ollama (local) and opencode_go are selectable per deployment. The default is mock mode — no external calls at all — so the core product runs without any AI provider configured.

AI derivation

Configurable prompt templates decompose stakeholder needs into system requirements. Every derivation can run in preview or write mode, and review policies decide whether the result is accepted automatically or waits for a human.

Semantic search & long-term memory

Self-hosted by default: in-process sentence-transformers embeddings stored in PostgreSQL with pgvector, plus full-text search with an RRF-fused semantic pass. Ollama or OpenAI embeddings and an external Honcho backend are opt-in alternatives.

Trace-link types

11 core link types, tenant-extensible

Each link type carries a meaning, so a traceability matrix says more than "these two artifacts are related". Every tenant can add its own types on top of the core catalog.

derives-from

The source was derived from the target — the downward path from needs to requirements.

decomposes

The target is a decomposition of the source — one artifact becomes many.

refines

A requirement refines a higher-level one — a refinement without the derivation obligation.

satisfies

A requirement satisfies a stakeholder goal — the coverage-relevant validation chain.

realizes

A requirement realizes a goal — the implementation claim, distinct from satisfaction.

allocated-to

A requirement or function is allocated to an architecture element or component.

verifies

A test case verifies a requirement — the path back up from tests to intent.

mitigates

A measure mitigates a risk, keeping the risk and its response connected.

decides

An ADR or decision affects the linked artifacts, documenting why they look the way they do.

references

A lightweight, non-deriving reference between two artifacts.

diagram-ref

An artifact is shown in or referenced by a diagram without a deriving relationship.

Rigor presets

The same product at three levels of formality

Rigor is a workspace setting, not a different installation. Switching the preset changes approvals and available baseline scopes while the data model stays identical.

Comparison of the minimal, standard and extended rigor presets
Dimension minimal standard extended
Approvals required No No Yes
Baseline scopes document document, project document, project, global
Typical fit Lightweight backlog Team and project delivery Formal systems engineering

Terminology profiles

The same entity can be labelled for a software team or for a systems-engineering audience. A dev-mode profile and an SE-mode profile change the vocabulary without changing the underlying data.

Enforced at runtime

Preset rules are checked by a runtime gate, not just documented: required approvals, baseline scopes and enabled features follow the workspace preset consistently across REST and MCP.

Enterprise

Isolation, auditability and operations

Features that matter once more than one team, more than one workspace and a compliance question enter the picture.

Multi-tenancy with row-level isolation

Every query is tenant-scoped through PostgreSQL row-level security and a thread-local TenantContext. Tenant data is isolated by the database, not by application convention.

RBAC and item-level permissions

A four-level role matrix (admin, approver, editor, viewer) plus per-item permissions for the cases where a workspace-wide role is not precise enough.

Operation-level audit log

Writes and their audit entries commit in the same transaction, so a rolled-back change never leaves an audit trail behind. Each artifact also exposes its own history endpoint.

Secrets encrypted at rest

Stored LLM provider API keys are encrypted with a dedicated encryption key. Production startup refuses to run without SECRET_KEY, JWT secret and encryption key configured.

Resilient by default

Retry, circuit-breaker and timeout decorators wrap service calls, and asynchronous work runs through Celery queues so a slow provider cannot stall the request path.

Backup and disaster recovery

A scheduled pg_dump sidecar keeps rotating database dumps, while an artifact-level disaster-recovery mechanism can snapshot and restore JSON backups independently.

German and English

The interface ships in both languages, and terminology profiles keep the vocabulary appropriate for each audience.

API keys for automation

Create, list and revoke API keys without sharing a user password, so CI/CD pipelines and MCP clients get scoped, revocable credentials.

Deployment

Tech stack and self-hosted quick start

ReqogniLoom is designed to be self-hosted with Docker Compose. The published stack pulls prebuilt images — no local build and no repository clone are required for a plain deployment.

Stack

  • Django 5.2+ backend (DRF, OpenAPI 3.0 via drf-spectacular)
  • React 18 + TypeScript 5.5 (strict) frontend
  • PostgreSQL 16 with pgvector for embeddings
  • Redis 7 as Celery broker and cache
  • Celery 5.3+ worker and beat scheduler

Compose services

The full stack runs eight services: postgres, postgres-backup, redis, migrate, backend, celery, celery-beat and frontend. A minimal compose file drops Celery, backup and optional profiles; an optional Honcho memory backend is available behind a compose profile.

Quick start

Two files are enough: the compose file and the environment example. Generate the required secrets, set the database passwords, then start the stack. Migrations and first-run self-initialization happen automatically in the migrate service.

mkdir reqogniloom && cd reqogniloom
RAW=https://raw.githubusercontent.com/Popoboxxo/ReqogniLoom/main

mkdir deploy
curl -fsSL -o deploy/docker-compose.yml "$RAW/deploy/docker-compose.yml"
curl -fsSL -o .env.example "$RAW/.env.example"
cp .env.example .env

# Generate the three required secrets and set DB_PASSWORD / DB_APP_PASSWORD in .env
python3 -c "import secrets; print(secrets.token_urlsafe(64))"   # SECRET_KEY, AUTH_JWT_SECRET
python3 -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"  # FIELD_ENCRYPTION_KEY

# .env is read at container creation, so use `up -d` after editing it
docker compose -f deploy/docker-compose.yml --project-directory . up -d
docker compose -f deploy/docker-compose.yml --project-directory . ps   # wait for "healthy"
curl -sf http://localhost:8001/health/                                 # {"status":"ok",...}

Endpoints after startup

The frontend is served on port 5173 by default and the backend REST/MCP endpoint on port 8001. Both are overridable in the environment file, which is useful when running a second instance on the same host.

Talk to the MCP server

Create an API key, then call a tool over JSON-RPC. A health check needs no authentication.

curl -X POST http://localhost:8001/mcp/ \
  -H "Content-Type: application/json" \
  -H "X-API-Key: reqlo_..." \
  -d '{"jsonrpc":"2.0","id":1,"method":"requirement.query",
       "params":{"workspace_id":"<id>","limit":5}}'
